## What "new_profiles" actually measures (verified, not assumed)

The task asked me to check whether "0 new profiles" means "0 signups" before
treating those as the same claim. I read supabase/migrations/20260318232431_...sql
and its later replacement 20260428062420_...sql: handle_new_user() is a
trigger on auth.users INSERT that unconditionally writes a profiles row
(with either the OAuth-provided name, the email local-part, or a
Dead-themed placeholder like "Sugar Magnolia 4271") for every signup,
regardless of provider. PickHandleModal.tsx (src/components/PickHandleModal.tsx)
only ever does an UPDATE on display_name — it never inserts. So:
new_profiles is a real signup-completion count, not a "picked a handle"
count. Six weeks with zero rows in that table is six weeks with zero
completed signups. This is the strongest, best-evidenced finding in this
report.

## Share loop status

Data-integrity finding that affects every "shares" number Jay was given:
share_events is not a pure share-action table. src/lib/trackShare.ts writes
real shares there (share_type = app_link/setlist/poster, channel =
copy_link/twitter/native_share/etc — fired from actual share-sheet
actions). But src/lib/trackCtaClick.ts (introduced 2026-04-23, commit
88c6ba2) also writes into the same table with share_type: "cta_click",
piggybacking specifically to avoid a migration. Callers include the landing
hero's "Build a Setlist" button (hero_build_setlist_guest,
src/components/landing/HeroSection.tsx), the poster page's two
guest-conversion CTAs (poster_build_setlist_guest_header and _bottom,
src/pages/SetlistPoster.tsx), the songbook/community links, and
announcement-bell clicks. So the 372-total "shares" figure (and every
monthly share_events number from April 23 onward) is a mix of "someone
shared a setlist" and "someone clicked a CTA button," with no way to tell
which is which from the aggregate alone. This needs a share_type breakdown
before anyone treats share_events as a share-loop health metric. I'm
flagging this rather than reinterpreting the given numbers, since I can't
query the split myself this run.

What the poster page (/setlist/:id, src/pages/SetlistPoster.tsx) does track
cleanly: a setlist_viewer_loaded PostHog event fires once per load with
auth_state (authenticated/anonymous) and referrer — this is exactly the
"who's arriving from a shared link, signed in or not" signal the share loop
needs, and it's wired correctly (confirmed by reading the effect, not
assumed). Audio playback on that page is instrumented via
audio_play_started / audio_track_advanced / audio_segue_completed /
audio_error / audio_autoplay_blocked (src/lib/player/audioInstrumentation.ts),
so "did the recipient actually press play" is answerable. The two guest
conversion CTAs on that page are tracked (into the conflated share_events
table, per above).

What's still invisible in the share loop:
- No event ties a specific share to the view(s) it produced. share_events
  has setlist_id and a timestamp; setlist_viewer_loaded has setlist_id and a
  timestamp; nothing joins "this share -> these N recipients" other than a
  manual time-window join in SQL, and PostHog (person/session-scoped) can't
  do that join at all since the sharer and the anonymous recipient are
  different identities.
- No "poster CTA shown but not clicked" signal — we only know clicks, not
  impressions, so CTA click-through rate is uncomputable.
- No completion event on the poster's guest path: a recipient can view,
  play, and click "Open the Builder," but nothing marks whether they
  actually signed up afterward. That link is only inferable via
  visitor_attribution + the link_visitor_to_user RPC (src/hooks/useAuth.ts),
  which requires a query I don't have this run.
- No channel-level signal for the "mostly iMessage" claim in my brief — the
  poster's referrer field will be empty for iMessage opens (iOS strips
  referrers for messaging-app links), so neither table currently
  distinguishes "iMessage" from "no referrer, unknown." If the share loop
  really is dominated by iMessage, that's structurally invisible to both
  systems as built. The channel field on an actual share action
  (native_share, sms, etc.) is the only place iMessage-adjacent intent
  shows up, and even that's the sender's channel choice, not proof of where
  the recipient came from.

## Landing to builder status

Guest/anonymous builder access has been live since 2026-03-23
(60b52ef/5f50153), which is good — that's the "build before auth"
architecture the brief asked me to verify. But there are two distinct guest
mechanisms in this codebase and only one of them is actually wired up:

- draft_setlists + RLS + getAnonDraftClient() (src/lib/anonSession.ts,
  shipped 2026-04-25, e58069d/60690c3/5f67121) is a real server-side
  anonymous-draft architecture with its own RLS smoke test
  (src/test/anonDraftRls.test.ts). I grepped every caller of
  getAnonDraftClient and draft_setlists in src/ and found none outside that
  test file and the auto-generated types. This is built but not shipped —
  confirms a correction already banked in CLAUDE.md.
- What actually ships: Builder.tsx's guestSlots — pure client-side React
  state, cached to sessionStorage under deadset-guest-cache only to survive
  an OAuth redirect round-trip (src/pages/Builder.tsx, lines roughly
  281-333). Nothing is written to Supabase or PostHog until the user
  authenticates, at which point the cached slots get replayed into a real
  setlists row.

The practical consequence for this priority: there is currently zero
visibility into anonymous builder activity that doesn't convert. No event
fires for "guest opened the builder," "guest added a song," "guest hit the
auth wall" (GuestSignInPrompt.tsx renders with no captureEvent call anywhere
in it — confirmed by reading the component), or "guest dismissed the prompt
with 'I'll keep building first.'" We only ever learn about a guest session
retroactively, and only if it converts, via setlist_created firing
post-auth. Every guest who builds and walks away is invisible by
construction. This is the single biggest blind spot for the top-of-funnel
priority, and it's also the cheapest to fix — the state already exists in
Builder.tsx, it just isn't captured.

Separately: the landing hero's primary CTA (hero_build_setlist_guest,
src/components/landing/HeroSection.tsx) reports only into the conflated
share_events/cta_click bucket, not into PostHog. So even the very top of
the funnel — "clicked Build a Setlist on the landing page" — isn't in
PostHog today, and is sitting in a table that mixes it with unrelated
clicks.

## Instrumentation-coverage audit (what PostHog can and can't answer, from here)

I read every posthog/captureEvent/captureException call site in src/ (16
files). Explicit-events-only is confirmed: src/lib/posthog.ts sets
disable_session_recording, autocapture, capture_dead_clicks, and
capture_heatmaps all to false/off and disable_surveys: true, with only
exception capture left on — matches the brief exactly.

What we can now answer, once data accumulates, that we couldn't before:
- Whether a /setlist/:id visitor is authenticated or anonymous, and their
  referrer, per load (setlist_viewer_loaded).
- Whether playback actually starts and whether track-to-track transitions
  are gapless in production (audio_play_started, audio_track_advanced with
  a gapless prop, audio_segue_completed, audio_error,
  audio_autoplay_blocked) — this is genuinely new signal; the first-party
  play_events table has no equivalent granularity.
- Share-sheet actions by type and channel (setlist_shared, from
  trackShare.ts — this one is not conflated, unlike its first-party twin).
- Setlist creation (setlist_created, fired from both useSetlist.ts and
  Builder.tsx).
- Comment posting (comment_posted), songbook issue opens
  (songbook_issue_opened), dispatch-email landings (dispatch_link_landed,
  UtmCapture.tsx), dispatch unsubscribes, and two narrow builder-entry
  events for the "score a show by date" flow (builder_date_mode_viewed,
  builder_date_mode_started, src/components/builder/ScoreShowByDate.tsx).
- Exceptions in the share-tracking and playback paths specifically (both
  wrap their try/catch in captureException).

What is still invisible — named gaps, in priority order for this product's
funnel (land -> build -> save -> share -> recipient plays):

1. Nothing between landing and a saved setlist for guests. No
   builder_opened, no guest_song_added, no auth_wall_shown, no
   auth_wall_dismissed, no auth_wall_accepted. This is the top-of-funnel
   bottleneck the brief names, and it is the least observable part of the
   entire app today.
2. No CTA impression tracking anywhere — only clicks. Every trackCtaClick
   and every PostHog click event answers "how many clicked," never "out of
   how many who saw it."
3. No signup-completion event in PostHog. useAuth.ts fires oauth_returned
   and email_confirmed into the first-party auth_events table via
   trackAuthEvent, but never calls captureEvent for a completed signup —
   PostHog's own view of "did this session convert" does not exist.
   identifyUser() runs on sign-in, which retroactively attaches future
   events to the person, but there's no discrete conversion event to build
   a funnel step on.
4. No share-to-view join possible, as covered above under "share loop
   status."
5. The Cosmic Charlie / AI-welcome-overlay wizard has a first-party
   equivalent (wizard_events: wizard_opened, priority_selected,
   generate_clicked, added 2026-08-13/14, 8ca8c90) but zero PostHog events.
   Given this is the literal "first Builder experience" shipped in the same
   March 23 wave that preceded the April spike, and it stops at
   generate_clicked with no "generation shown," "setlist accepted," or
   "setlist discarded" event on either system, it's currently impossible to
   tell whether the wizard converts lookers into savers or just produces
   noise. Worth naming since it wasn't in the priorities list but sits
   directly on top of "land -> build."
6. No mobile/desktop or new/returning dimension is captured explicitly
   anywhere — PostHog's device/browser properties come for free from the
   SDK once events accumulate, so this resolves itself over the next few
   weeks; flagging only so it isn't assumed solved today.

## Whether first-party tables and PostHog overlap or conflict

They mostly answer different questions today, with one real overlap and one
real gap in the first-party side worth naming:

- No conflict on shares specifically once you split share_type.
  trackShare.ts writes the same conceptual event to both systems
  (share_events row + setlist_shared PostHog event) for real shares — that's
  intentional duplication, not conflict, and it's fine to keep: the
  first-party table is the system of record (has setlist_id, ties to
  visitor_id/user_id for later SQL joins with visitor_attribution and
  profiles), PostHog is where funnel/cohort tooling lives. Don't retire
  either side of that pair.
- Overlap-with-conflation risk: share_events also carries cta_click rows
  from five different surfaces (landing hero, poster page x2,
  announcements, browse-community links) that have no PostHog counterpart
  at all. If someone builds a PostHog funnel assuming share_events equals
  "shares," they'll double-count clicks as shares; if someone reads
  share_events in Supabase without filtering share_type, same problem.
  Recommend either giving cta_click its own table or at minimum documenting
  the split — not urgent, but cheap to fix now before more callers are
  added.
- wizard_events and auth_events have zero PostHog presence. These are
  first-party-only today. That's fine as long as it's a choice, not an
  oversight — right now it reads like an oversight, since trackAuthEvent and
  trackWizardEvent were clearly written before PostHog existed in this
  codebase and nobody went back to add the PostHog side once the wizard
  landed.
- Net recommendation: keep both, don't retire either. The first-party
  tables are the durable, queryable system of record with real joins
  available (visitor-to-user attribution, setlist ownership, RLS-scoped
  access) and six months of history; PostHog is additive for
  session/funnel/cohort analysis and device/browser dimensions the
  first-party tables don't capture. The actual fix is closing the gaps
  named above, not consolidating systems.

## This week's experiment

Status of last week's experiment: none — this is the first growth review in
this repo (reports/growth/ did not exist before this run).

Hypothesis: the guest-builder auth wall (GuestSignInPrompt) is where most
anonymous builder sessions die, and because nothing captures the moment it
appears or how the user responds, that drop-off is currently invisible —
which is also why conversion (new_profiles/uniques) has fallen from 8.2% in
March to roughly 0-2.5% every month since, even as auth-friction-removal
work shipped.

Single change to make: instrument the existing guest-builder flow in
Builder.tsx and GuestSignInPrompt.tsx with four PostHog events —
guest_builder_started (guest mode entered, i.e. isGuestMode becomes true),
guest_song_added (each push to guestSlots), auth_wall_shown (the prompt
renders), and auth_wall_response (action: sign_in or dismiss). No copy
changes, no UX changes — purely additive event capture on state transitions
that already exist in the component. This is a measurement change, not a
funnel change, deliberately: we don't yet know where the drop-off is, so
there's nothing to A/B test yet.

Measured by: the four new PostHog events above, funneled against the
existing setlist_created event (fires post-auth) to compute
guest_builder_started -> guest_song_added -> auth_wall_shown ->
auth_wall_response(sign_in) -> setlist_created as a real step-by-step
funnel for the first time.

Decision threshold: after two weeks of data (given ~40 users and currently
single-digit-to-low-hundreds monthly traffic, one week is very likely too
thin to read) — if guest_song_added -> auth_wall_shown -> sign_in shows a
drop-off below 50% at any single step, that step becomes next week's actual
experiment target (copy, timing, or removing the wall entirely at that
step). If instead the funnel shows guests aren't reaching
guest_builder_started in meaningful numbers at all, the real bottleneck is
upstream on the landing page, not the builder — reroute the next experiment
there instead.
