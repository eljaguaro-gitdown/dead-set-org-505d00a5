# Growth Review — 2026-08-15
## Special topic: PostHog dead-instrumentation audit (decision-ready for Jay)

**Scope note:** Not the standard weekly WoW funnel — Jay asked for a decision-ready read on a measurement problem: PostHog has never actually loaded in production (verified independently against the live bundle; see task brief — not re-derived here). No lost data, no backfill possible. This report enumerates the dead call sites, scores Supabase-table coverage, and commits to one path forward. Full weekly WoW funnel review resumes next week once this is resolved.

**Recommendation, up front: Option 2 — delete the dead `posthog.capture` call sites and standardize on the Supabase-table pattern. Do not install `posthog-js`.**

Reasoning in brief (full detail in §4):
1. The codebase has already converged on the Supabase pattern **three separate times independently** — `wizard_events` (shipped 2026-08-14, the day before this audit), `trackCtaClick` (piggybacks on `share_events` specifically to avoid a new PostHog-style tool), and `track-visit`/`page_visits`. Nobody had to be told to do this; it's the path of least resistance in this repo already.
2. Two prior growth-analyst passes (`reports/growth/2026-08-08-signup-attribution.md`, `2026-08-09-ig-cohort-first-visit.md`) already burned real analyst time on "re-run once PostHog access is restored" follow-up lists that could never be executed. That's not a one-time cost — it recurs every week Option 1's promise stays unfulfilled, and it already recurred twice before anyone noticed why.
3. iOS: `ios/App/App/PrivacyInfo.xcprivacy` explicitly declares `NSPrivacyTracking = false`, an empty `NSPrivacyTrackingDomains` array, and states in its own header comment "No third-party analytics, attribution, or tracking SDKs are bundled." Installing PostHog means touching that file, `PrivacyPolicy.tsx`, and the App Store Connect privacy questionnaire, and reasoning carefully about whether PostHog's default person-profile/cross-session identification counts as "tracking" under Apple's definition — real compliance surface for a 40-person closed beta.
4. Brand/stewardship posture: the field guide's own Insight 06 says "No sensitive personal data is collected — music preferences and auth only." A third-party analytics vendor capturing IP, device fingerprint, and behavioral data by default cuts against that self-description even though it's internal-only language.
5. Bundle/operational weight: the standard PostHog install is an async snippet from a third-party host (new CSP consideration, new script tag where `index.html` currently has none, and event loss from ad-blockers — a real risk with a privacy-conscious, technically literate Deadhead audience). The `posthog-js` npm path avoids the CSP issue but adds real bundle weight and moves init into app code that can fail silently — exactly the failure mode that produced this audit in the first place.
6. What Option 1 buys that Option 2 doesn't get for free: no-code funnels/retention/cohort UI and session replay. That's real, and matters more as the team or user base grows (see "What would flip this," end of report). At 40 users it's not worth the compliance and reliability cost today.

## 3. Genuinely missing measurement, prioritized by decision value

Given only the Supabase tables that exist today, here is what Jay **cannot** answer, ranked by how much it blocks the two standing priorities:

1. **Landing → Builder, step by step (standing priority #1).** There is no SPA-level pageview log anywhere. `VisitorTracker.tsx` (writes `page_visits`) mounts once, at the app shell's root, with an empty dependency array — it fires **once per full page load**, not on every client-side route change. `UtmCapture.tsx` *does* re-run on every route change (its `useEffect` depends on `location.pathname`), but it never wrote to Supabase — only to PostHog, which was never there. Net effect: an anonymous visitor who lands on `/`, then client-side-navigates to `/builder`, produces **one** `page_visits` row (`/`) and nothing for `/builder` unless they separately trigger `wizard_events` (which only fires when the Cosmic Charlie dialog opens — not on plain arrival, and not for the date-mode door). **You cannot currently reconstruct the landing→builder step of the funnel from Supabase data at all**, independent of the anonymous-draft-mode question the standing brief asks about.
2. **Share-loop entry, segmented by auth state (standing priority #2).** `setlist_viewer_loaded` was the only signal recording whether a `/setlist/:id` visitor arrived signed-in or anonymous, with referrer, at the exact moment of poster-page load. Nothing replaces this. Compounding it: per the 2026-08-09 ad-hoc report, the poster page's own "Build your own dream show" CTA at the bottom (`SetlistPoster.tsx:997`, `trackCtaClick("poster_build_setlist_guest_bottom", ...)`) **is** tracked into `share_events` — so the exit side of the share loop is measured, but the entry side (who's landing, anonymous vs. not) is not.
3. **Gapless-audio quality signal.** `audio_track_advanced`'s `gapless` boolean and `audio_segue_completed` were built specifically to catch production-only CORS/preload degradation in the gapless engine — the code comment says so directly. Given that "finish-rate improved significantly after the play_events fix" is a standing fact Jay already relies on, there is currently **no way to confirm that improvement is holding, or to catch a regression**, because the one signal built to watch it never shipped live.
4. **Builder date-mode funnel** (`viewed → started → completed / no_show_found`). This is a whole entry path into the builder ("Score a Show by Date") with zero visibility today — not even a raw count of how many builder sessions see that door.
5. **Dispatch email funnel edges** (`dispatch_link_landed`, `dispatch_unsubscribed`). Lower priority — the durable state (`profiles.dispatch_opt_in`, `visitor_attribution` first touch) covers the coarse question ("is this person still opted in / did they ever arrive from a dispatch"), just not the time-series/per-send breakdown a real email-funnel review would want.

## 4. Option decision (detail)

**What Option 1 (install `posthog-js`) buys:** point-and-click funnels, retention/cohort analysis, session replay, no hand-written SQL per question — a real ergonomics win, and matches the field guide's own "operator profile" (founder works through Lovable's cloud UI, limited CLI familiarity — HogQL in a web UI is a better fit for that profile than psql).

**What it costs:**
- **iOS compliance surface.** `PrivacyInfo.xcprivacy` currently makes a clean, defensible claim (`NSPrivacyTracking = false`, no tracking domains, no third-party SDKs). PostHog's ingestion host would need to be declared, and someone has to determine — correctly, not by assumption — whether PostHog's default configuration (person profiles, cross-session device ID) trips Apple's tracking definition. Getting this wrong risks an App Store rejection or a privacy-nutrition-label mismatch, either of which is a much worse failure mode than "no data this week."
- **Bundle/CSP/reliability.** The standard install is a third-party async script (new CSP surface, ad-blocker loss); the npm path avoids CSP but adds bundle weight and moves init into app code — which is the exact class of failure (silent, undetected for the life of the repo) that caused this audit.
- **Brand/stewardship fit.** Minor but real: the field guide already touts minimal data collection as a value (Insight 06). A third-party behavioral-analytics vendor is a step away from that, even if it never appears in user-facing copy.
- **It doesn't fix anything by itself.** Every event in §1 would still need code review to confirm it actually fires correctly once PostHog is live (e.g., is `ph?.capture` really being called with the right props post-refactor?) — the same verification discipline Option 2 requires anyway.

**What Option 2 costs, concretely:** hand-built SQL views/RPCs instead of a UI, and hand-rolled cohort logic instead of PostHog's cohort builder. At **~40 users**, this is a non-issue — a `GROUP BY` a growth-analyst session runs ad hoc, or a small admin RPC mirroring the existing `get_admin_traffic_stats` pattern, covers it. The "15-event activation funnel" the field guide describes doesn't need a dedicated analytics platform to answer "how many people did X then Y" at this scale; it needs 4-6 well-designed Supabase views. The repo already has the muscle memory for this (`get_admin_traffic_stats`, `admin_traffic_stats_cache`, `mark_ab_conversion`).

**Verdict: Option 2.** The codebase converged here on its own before this audit even started; formalizing that is lower-risk, lower-cost, and fits the team's actual working pattern (Supabase + Lovable, not a third SaaS analytics tool) better than reviving a dependency that silently failed for the entire life of the product without anyone noticing.

### What has to be built in-house to replace what PostHog would have given

- **Funnels:** no generic funnel UI — replace with purpose-built SQL views/RPCs per funnel, same shape as `get_admin_traffic_stats`. Estimate: 1 migration + 1 admin-readable RPC per funnel, ~1-2 hours each for a build session. The activation funnel likely collapses to 4-6 Supabase-backed steps once the gaps in §3 are closed (most of the raw event coverage already exists; it's the SQL layer that's missing, not the underlying data).
- **Retention/cohorts:** no cohort builder — a small materialized view or scheduled aggregation (mirroring `admin_traffic_stats_cache`'s refresh-on-demand pattern) covers "week N retention" at this scale. Roughly half a day of build-session time; not urgent while the cohort is ~40 people.
- **Segmentation (device, new/returning, entry path):** already mostly available — `page_visits.user_agent`, `visitor_attribution.first_source`, and `auth_events`/`play_events` timestamps are enough to derive device class and new-vs-returning without any new instrumentation, just SQL.

## 5. Migration / cleanup plan — Option 2

Small, ordered, each step independently shippable. Route each to a build session; this analyst does not edit `src/`.

1. **Delete the dead code paths.** Remove all 13 call sites/patterns in §1 (the 7 files: `SetlistPoster.tsx`, `Unsubscribe.tsx`, `Builder.tsx`, `audioInstrumentation.ts` + its call sites in `AudioPlayerContext.tsx`, `UtmCapture.tsx`, `ScoreShowByDate.tsx`). Zero behavior change, zero risk — ships immediately, independent of everything below. Also stops any future analyst session from wasting time on "PostHog follow-up" lists that can never execute, which has already happened twice (2026-08-08, 2026-08-09 reports).
2. **Close gap #1 (landing→builder):** add a lightweight `page_view_events` table (or extend `page_visits` with a route-level insert) and fire it on every SPA route change — mirror `UtmCapture.tsx`'s existing `useEffect([location.pathname])` pattern rather than `VisitorTracker.tsx`'s mount-once pattern. Highest-value single change on this list.
3. **Close gap #2 (share-loop entry):** restore `setlist_viewer_loaded`'s content (`auth_state`, `referrer`, `setlist_id`) as an insert on `SetlistPoster.tsx` mount, either into the new table from step 2 (with a `metadata` column) or share_events with a new `share_type`. Pairs directly with the already-working `poster_build_setlist_guest_bottom`/`_header` CTA tracking to finally close the share-loop funnel end to end.
4. **Close gap #3 (audio quality):** extend `play_events` with nullable columns (`engine`, `gapless`, `autoplay_blocked`, `error_message`) or add a small `audio_quality_events` table, and wire `AudioPlayerContext.tsx`'s existing `captureAudioEvent` call sites to it instead of `window.posthog`. Directly supports verifying the play-events/finish-rate fix is holding.
5. **Close gap #4 (builder date-mode funnel):** extend `wizard_events`'s `event_name` check constraint to add `builder_date_mode_viewed/started/completed/no_show_found` (or a parallel `mode='date'` value) — cheap, since the table was purpose-built for exactly this shape one day before this audit.
6. **Close gap #5 (dispatch funnel edges), lowest priority:** add `dispatch_id`-linked rows to `auth_events` (or a small `dispatch_events` table) for link-landed and unsubscribe actions.
7. **Docs follow-up (not mine to make):** `dead-set-field-guide.md`'s "Analytics: PostHog" row and "Analytics discipline" section (§3A, §5C) describe a tool that was never live. Flag to Jay/community-steward to update once steps 1-6 land, so the internal grounding doc matches reality.

## What would flip this back to Option 1

Revisit if: the user base grows well past the point where ad hoc SQL keeps up (hundreds+ active users), a dedicated non-technical growth hire needs point-and-click funnel/cohort tools day to day, or qualitative session-replay becomes worth the compliance cost. If so, prefer a self-hosted or EU-region PostHog instance with tracking/cross-session identification explicitly disabled (to preserve the `NSPrivacyTracking = false` iOS story), and ship it with a startup health-check that logs to Supabase if `window.posthog` fails to initialize within a few seconds — so this exact failure mode (silent no-op, undetected for months) cannot recur unnoticed.
